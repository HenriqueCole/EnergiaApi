1. O projeto

A EnergiaApi é um webservice de eficiência energética e sustentabilidade escrito em ASP.NET Core 8, reaproveitado dos desafios anteriores da trilha. Ela monitora o consumo de energia de equipamentos urbanos, dispara alerta quando o consumo passa do limite configurado e monta relatórios agregados. É a base de dados que uma cidade usaria para decidir onde cortar desperdício.

Nesta fase, o objetivo não era mexer nas regras de negócio e sim colocar a aplicação para funcionar como funcionaria de verdade: build, teste, empacotamento e entrega em dois ambientes, tudo automatizado, com a configuração saindo do código para poder variar por ambiente.

2. O pipeline

A ferramenta escolhida foi o GitHub Actions. O motivo é prático: ele fica no mesmo lugar do código, não tem servidor de build para manter, os runners já vêm com Docker e Compose instalados, e o recurso de Environments resolve separação de segredos e aprovação manual sem precisar de mais nada.

As imagens vão para o GitHub Container Registry, que também é integrado ao repositório e autentica com o GITHUB_TOKEN do próprio run.

O pipeline inteiro roda no push da main. Em pull_request para a main, só o build e os testes rodam, para barrar código quebrado antes do merge. O workflow_dispatch permite disparar na mão.

Etapas

push na main
  │
  ├─▶ 1. build-test ........... restore, build Release, dotnet test (xUnit), artefato .trx
  │
  ├─▶ 2. image ................ build da imagem, push no GHCR (tags :sha-curto e :latest)
  │
  ├─▶ 3. deploy-staging ....... environment "staging", pull, compose up, smoke test
  │
  └─▶ 4. deploy-production .... environment "production" com aprovacao manual, mesma imagem, smoke test
#JobO que fazPor quê
1build-test Roda dotnet restore, dotnet build -c Release e dotnet test com os 6 testes de integração. O relatório .trx fica salvo como artefato do run. Se a compilação ou um teste falhar, nenhum job depois dele começa.
2image Constrói a imagem pelo Dockerfile e publica no GHCR com as tags :<sha-curto> e :latest, aproveitando o cache de camadas do Actions (type=gha). Gera um artefato único, identificado pelo commit, que os dois ambientes vão usar.
3deploy-staging Login no GHCR, docker compose --env-file .env.staging -p energia-staging up -d --no-build e smoke test na porta 8081. No fim imprime os logs da aplicação. Testa a imagem em um ambiente igual ao de produção antes de qualquer coisa chegar no usuário.
4deploy-production Só roda se staging passou (needs: deploy-staging) e sobe a mesma imagem com .env.production na porta 8082, seguido do smoke test. Produção recebe exatamente o binário que passou em staging, sem rebuild. Aquele bug de "mas funcionava em staging" simplesmente não existe.

Testes

A suíte xUnit sobe a API em memória com WebApplicationFactory e banco InMemory. São 6 testes, cobrindo os 5 endpoints de negócio e o /health:

$ dotnet test
Passed!  - Failed: 0, Passed: 6, Skipped: 0, Total: 6, Duration: 586 ms

Fora isso, cada deploy passa pelo smoke test, que testa o ambiente já publicado: espera o /health responder, autentica em /api/auth/login, consulta /api/consumos (é aqui que se prova que a API fala com o banco e que as migrations rodaram) e chama a rota protegida /api/alertas com o token. Qualquer passo que falhe derruba o job.

Ambientes e segredos

Os dois deploys usam GitHub Environments, um staging e outro production. Com isso, a URL de cada ambiente aparece na tela do run, os segredos ficam separados por ambiente, e a produção pode exigir aprovação manual. O DB_PASSWORD e o JWT_KEY entram no container como variável de ambiente, então nunca aparecem no código nem dentro da imagem.

A aprovação manual é configurada em Settings, Environments, production, Required reviewers. Se os segredos não estiverem cadastrados, o workflow usa os valores dos arquivos .env.* e roda do mesmo jeito. Fiz assim para o projeto poder ser clonado e testado sem configuração prévia.

Dockerfile

# Estagio 1: build e publish. Usa o SDK, que e uma imagem grande, e some no final.
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src

# Copia so o .csproj primeiro. Enquanto as dependencias nao mudam,
# o Docker reaproveita a camada de restore que ja esta em cache.
COPY ["EnergiaApi.Api/EnergiaApi.Api.csproj", "EnergiaApi.Api/"]
RUN dotnet restore "EnergiaApi.Api/EnergiaApi.Api.csproj"

COPY . .
RUN dotnet publish "EnergiaApi.Api/EnergiaApi.Api.csproj" \
    -c Release --no-restore -o /app/publish

# Estagio 2: runtime. So o ASP.NET Core, sem SDK e sem codigo-fonte.
FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS final
WORKDIR /app
COPY --from=build /app/publish .

ENV ASPNETCORE_URLS=http://+:8080
EXPOSE 8080

# Roda com usuario sem privilegios. O APP_UID=1654 ja vem definido na imagem base.
USER $APP_UID

ENTRYPOINT ["dotnet", "EnergiaApi.Api.dll"]
EstratégiaComoResultado
Build em dois estágiosEstágio build com o SDK, estágio final só com o runtimeA imagem entregue não leva SDK, compilador nem código-fonte. Fica mais leve e com menos coisa exposta
Cache de camadasCOPY do .csproj e restore antes do códigoMexer no código não re-baixa os pacotes NuGet. No pipeline o cache também é reaproveitado, com type=gha
Usuário sem privilégiosUSER $APP_UIDO processo não roda como root dentro do container
.dockerignoreIgnora bin, obj, node_modules e frontendContexto de build menor e build que dá o mesmo resultado sempre
Configuração por foraNenhuma senha ou connection string dentro da imagemA mesma imagem roda nos três ambientes. Só o --env-file muda

Os três recursos que a atividade pede

RecursoOnde estáPara que serve
Volumemssql-data:/var/opt/mssqlOs dados do banco sobrevivem ao docker compose down e à recriação do container
Redeenergia-net, uma bridge dedicadaAPI e banco se acham pelo nome do serviço (Server=mssql,1433) e ficam isolados de outras stacks
Variáveis de ambiente.env, .env.staging, .env.productionPorta, nome do banco, ASPNETCORE_ENVIRONMENT, senha e chave JWT fora do código
O depends_on: condition: service_healthy cuida da ordem de subida. A API só inicia depois que o SQL Server responde na 1433, o que evita aquele erro de migration em container que sobe mais rápido que o banco.

5. O que deu trabalho

ProblemaO que estava acontecendoComo resolvi
SQL Server no Mac A imagem mssql/server não tem build para ARM64 e o container não subia na minha máquina. Troquei para mcr.microsoft.com/azure-sql-edge, que tem imagem ARM64 e x86. Com isso a mesma stack roda no meu Mac e no runner Linux do GitHub.
A API subia antes do banco As migrations rodam no startup e falhavam porque o SQL Server ainda estava inicializando. healthcheck no serviço mssql batendo na porta 1433, mais depends_on: condition: service_healthy na API. O EnableRetryOnFailure() do EF Core cobre o resto.
Migrations quebrando os testes Os testes usam banco InMemory, que não aceita Database.Migrate(). Um if (!app.Environment.IsEnvironment("Testing")) no Program.cs. A ApiFactory dos testes sobe com UseEnvironment("Testing").
Senha dentro do compose A senha do banco e a chave JWT estavam fixas no docker-compose.yml e no appsettings.json. Tudo virou variável de ambiente, com ${DB_PASSWORD:?...} falhando na hora se faltar. Em CI os valores vêm dos secrets. O .env entrou no .gitignore e só o .env.example ficou versionado.
Dois ambientes na mesma máquina Staging e produção brigavam por porta, nome de container e volume. Um compose só, parametrizado, com um --env-file por ambiente (8081 e 14331 contra 8082 e 14332) e o -p separando containers, rede e volume.
Nome da imagem no GHCR O push falhava com erro de nome inválido, porque github.repository vem com letra maiúscula e o GHCR só aceita minúscula. Um passo que normaliza o nome com REPO="${GITHUB_REPOSITORY,,}" e expõe a tag como output do job.
Healthcheck dentro do container A imagem aspnet:8.0 não tem curl nem wget, então um healthcheck HTTP no compose exigiria instalar pacote e engordar a imagem. Deixei a imagem enxuta e passei a validar de fora, com o scripts/smoke-test.sh. É o mesmo script que roda no pipeline e na minha máquina.
Provar qual ambiente respondeu O Swagger só era registrado em Development, e nada na resposta dizia em qual ambiente a API estava rodando. Ficava difícil evidenciar isso num print. Criei o /health devolvendo ambiente e versao, que é o SHA do commit, e liberei o Swagger também em Staging.
Bit de execução no ZIP Ao empacotar o projeto, o smoke-test.sh perdia a permissão de execução. Quem extraísse o ZIP e desse push teria o pipeline falhando com "permission denied". O workflow chama bash scripts/smoke-test.sh em vez de ./scripts/smoke-test.sh, e o empacotamento preserva o modo do arquivo.
