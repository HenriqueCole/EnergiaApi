1. Visão geral do projeto

A EnergiaApi é um webservice RESTful de eficiência energética e sustentabilidade (ESG) desenvolvido em ASP.NET Core 8, reaproveitado dos desafios anteriores da trilha. A aplicação monitora o consumo de energia de equipamentos urbanos, gera alertas automáticos quando o consumo excede o limite configurado e produz relatórios agregados — a base de dados para decisões de eficiência energética de uma cidade inteligente.

Neste desafio a aplicação foi adaptada para simular um ambiente de produção real: o ciclo de vida inteiro (build, teste, empacotamento e entrega em dois ambientes) passou a ser automatizado, e a configuração foi externalizada para que a mesma imagem rode em desenvolvimento, homologação e produção.

2. Descrição do pipeline

Ferramenta: GitHub Actions. Escolhida por ficar no mesmo lugar do código-fonte — sem servidor de build para manter, com runners hospedados que já trazem Docker e Compose instalados, e com o recurso de Environments, que entrega separação de segredos e aprovação manual sem nenhuma ferramenta extra.

Registro de imagens: GitHub Container Registry (GHCR), também integrado ao repositório e autenticado com o GITHUB_TOKEN do próprio run.

Gatilhos: push na main executa o pipeline completo; pull_request executa apenas build e testes, barrando código quebrado antes do merge; workflow_dispatch permite execução manual.

Etapas

push na main
  │
  ├─▶ 1. build-test ........... restore → build Release → dotnet test (xUnit) → artefato .trx
  │
  ├─▶ 2. image ................ build da imagem → push no GHCR (tags :sha-curto e :latest)
  │
  ├─▶ 3. deploy-staging ....... environment "staging" → pull → compose up → smoke test
  │
  └─▶ 4. deploy-production .... environment "production" (aprovação manual) → mesma imagem → smoke test
#JobO que fazLógica / por quê
1build-test dotnet restore, dotnet build -c Release e dotnet test com os 6 testes de integração. O relatório .trx sobe como artefato do run. Portão de qualidade: nenhum job seguinte começa se a compilação ou um teste falhar.
2image Constrói a imagem pelo Dockerfile e publica no GHCR com as tags :<sha-curto> e :latest, com cache de camadas do Actions (type=gha). Produz um artefato imutável identificado pelo commit, que será promovido pelos dois ambientes.
3deploy-staging Login no GHCR, docker compose --env-file .env.staging -p energia-staging up -d --no-build e scripts/smoke-test.sh contra a porta 8081. Publica os logs da aplicação no fim do job. Valida a imagem em um ambiente equivalente ao de produção antes de qualquer exposição ao usuário final.
4deploy-production Depende do sucesso de staging (needs: deploy-staging) e sobe a mesma imagem com .env.production na porta 8082, seguido do smoke test. Promoção de artefato: produção recebe exatamente o binário aprovado, sem rebuild — elimina a classe de bug “funcionava em staging”.

Testes automatizados

A suíte xUnit sobe a API em memória com WebApplicationFactory e banco EF Core InMemory, cobrindo os 5 endpoints de negócio e o /health:

$ dotnet test
Passed!  - Failed: 0, Passed: 6, Skipped: 0, Total: 6, Duration: 586 ms

Além disso, cada deploy é verificado pelo smoke test, que exercita o ambiente já publicado: aguarda o /health, autentica em /api/auth/login, consulta /api/consumos (provando que a API alcança o banco e que as migrations rodaram) e chama a rota protegida /api/alertas com o token JWT. Qualquer passo que falhe derruba o job e o deploy é considerado quebrado.

Ambientes e segredos

  • GitHub Environments staging e production: cada um com sua URL exibida na tela do run e seus próprios segredos.
  • Segredos por ambiente: DB_PASSWORD e JWT_KEY são injetados como variáveis de ambiente no container — nunca ficam no código nem na imagem.
  • Aprovação manual em produção: configurada em Settings → Environments → production → Required reviewers, o que transforma o último job em um deploy sob aprovação.
  • Fallback: sem os secrets configurados, o workflow usa os valores dos arquivos .env.* e roda de ponta a ponta em qualquer fork, sem configuração prévia.

Dockerfile

# --- Estagio 1: build/publish (SDK, imagem grande, descartada no final) ---
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src

# Copia so o .csproj primeiro: enquanto as dependencias nao mudam,
# o Docker reaproveita a camada de restore em cache.
COPY ["EnergiaApi.Api/EnergiaApi.Api.csproj", "EnergiaApi.Api/"]
RUN dotnet restore "EnergiaApi.Api/EnergiaApi.Api.csproj"

COPY . .
RUN dotnet publish "EnergiaApi.Api/EnergiaApi.Api.csproj" \
    -c Release --no-restore -o /app/publish

# --- Estagio 2: runtime (so o ASP.NET Core, sem SDK nem codigo-fonte) ---
FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS final
WORKDIR /app
COPY --from=build /app/publish .

ENV ASPNETCORE_URLS=http://+:8080
EXPOSE 8080

# Roda como usuario sem privilegios (APP_UID=1654 ja vem definido na imagem base).
USER $APP_UID

ENTRYPOINT ["dotnet", "EnergiaApi.Api.dll"]
EstratégiaImplementaçãoGanho
Multi-stage buildEstágio build com SDK; estágio final só com o runtimeA imagem entregue não carrega SDK, compilador nem código-fonte: menos peso e menor superfície de ataque
Cache de camadasCOPY do .csproj + restore antes do códigoMudar código não re-baixa pacotes NuGet; no pipeline o cache é reaproveitado via type=gha
Usuário sem privilégiosUSER $APP_UIDO processo não roda como root dentro do container
.dockerignoreIgnora bin, obj, node_modules, frontendContexto de build enxuto e reproduzível
Configuração externalizadaNenhuma senha ou connection string dentro da imagemA mesma imagem roda nos três ambientes — só o --env-file muda

Orquestração: os três recursos exigidos

RecursoOndePara que
Volumemssql-data:/var/opt/mssqlOs dados do banco sobrevivem ao docker compose down e à recriação do container
Redeenergia-net (bridge dedicada)API e banco se enxergam pelo nome do serviço (Server=mssql,1433) e ficam isolados de outras stacks
Variáveis de ambiente.env, .env.staging, .env.productionPorta, nome do banco, ASPNETCORE_ENVIRONMENT, senha e chave JWT fora do código
depends_on: condition: service_healthy garante a ordem de subida: a API só inicia depois que o SQL Server responde na 1433, o que evita o erro clássico de migration em container que sobe mais rápido que o banco.

5. Desafios encontrados e como foram resolvidos

DesafioO que aconteciaSolução adotada
SQL Server em Apple Silicon A imagem mssql/server não tem build ARM64; o container não subia na máquina de desenvolvimento. Troca para mcr.microsoft.com/azure-sql-edge, que tem imagem ARM64 e x86 — a mesma stack roda no Mac e no runner Linux do GitHub.
API subindo antes do banco As migrations do EF Core rodam no startup e falhavam porque o SQL Server ainda estava inicializando. healthcheck no serviço mssql testando a porta 1433 + depends_on: condition: service_healthy na API, reforçado por EnableRetryOnFailure() no EF Core.
Migrations quebrando os testes Os testes usam banco InMemory, que não suporta Database.Migrate(). Guarda if (!app.Environment.IsEnvironment("Testing")) no Program.cs; a ApiFactory dos testes sobe com UseEnvironment("Testing").
Segredos no compose Senha do banco e chave JWT estavam fixas no docker-compose.yml e no appsettings.json. Tudo passou a vir de variável de ambiente, com ${DB_PASSWORD:?...} falhando rápido se faltar. Em CI os valores vêm dos secrets do GitHub Environment; .env ficou no .gitignore e só o .env.example é versionado.
Dois ambientes na mesma máquina Staging e produção colidiam em portas, nomes de container e volumes. Um único docker-compose.yml parametrizado + um --env-file por ambiente (portas 8081/14331 e 8082/14332) + -p para isolar containers, rede e volume de cada um.
Nome de imagem no GHCR O push falhava com erro de nome inválido porque github.repository vem com letras maiúsculas e o GHCR exige minúsculas. Passo que normaliza o nome com expansão do bash — REPO="${GITHUB_REPOSITORY,,}" — e expõe a tag como output do job.
Healthcheck dentro do container A imagem aspnet:8.0 não traz curl nem wget, então um healthcheck HTTP no compose não funcionaria sem instalar pacote extra e engordar a imagem. Manter a imagem enxuta e validar a subida de fora, pelo scripts/smoke-test.sh, que é o mesmo script usado no pipeline e localmente.
Evidenciar o ambiente certo O Swagger só era registrado em Development, e nada na resposta da API dizia em qual ambiente ela rodava — difícil provar nos prints qual instância respondeu. Endpoint /health devolvendo ambiente e versao (o SHA do commit), e Swagger habilitado também em Staging.
Divergência entre ambientes Rebuildar a imagem em cada deploy abre espaço para produção receber um binário diferente do que passou em staging. A imagem é construída uma única vez, marcada com o SHA do commit, e os dois deploys usam --no-build sobre a mesma tag: promoção de artefato em vez de reconstrução.
